| ADR-014 | Phase 07 Terraform (unapplied, unvalidated): private-IP-only Cloud SQL via Private Services Access + Cloud Run Direct VPC egress (`PRIVATE_RANGES_ONLY`, no NAT/connector); relay and dispatcher are two internal services sharing the app image; worker job `max_retries = 0`; bucket prefixes `input/`/`staging/`/`published/` with 1-day `staging/` lifecycle; generated DB password in Secret Manager and local Terraform state; schedulers paused and placeholder images by default | Keeps the DB off the internet without fixed-cost network components; separate services give relay/dispatcher their own identities as SECURITY.md requires; retries stay owned by the DB lease so Cloud Run, Pub/Sub and app retries do not multiply; local state avoids a bootstrap bucket. | ADR-013 | Phase 06 uses a local durable file queue, synchronous bounded Docker runner, existing state-dependent lease_until and compact job/attempt output paths | Tests actual DB/media/recovery without cloud services or dependencies; job identity preserves source/profile while compact UUID hex paths avoid Windows MAX_PATH. Queue requires repeated CLI cycles and private orphan files need disk monitoring | Phase 08 implements real Pub/Sub/Cloud Run/GCS and independent dispatch; verify lease timing and add bounded orphan cleanup before sustained use |
| ADR-015 | **Deployment target is a self-managed Windows Server VPS (3 vCPU, 4 GB), not GCP** (owner decision, 2026-11-17). Supersedes ADR-001, 003 (Cloud SQL part), 004, 005, 006 (Pub/Sub part), 008 and 014 for production; `infra/` and the GCP docs are archived, never applied | The VPS is already paid for, software cost target is 0, and the owner wants one machine that is simple to operate. Costs: one failure domain (machine, disk, database), no managed backups/monitoring, no container isolation, and a departure from the brief's "AWS/Azure/GCP", "container-based transcoding" and "infrastructure from code" wording that needs instructor confirmation | Instructor rejects a non-cloud host; VPS proves too small in measured tests |
| ADR-016 | PostgreSQL table `queue_messages` replaces Pub/Sub (`app/queue_pg.py`): at-least-once delivery, `FOR UPDATE SKIP LOCKED`, 300 s visibility timeout, 10-delivery cap then dead row. The Phase 06 outbox, relay, claim/lease and reconcile code is reused unchanged; the worker relays one event only when the queue is empty | No extra service or dependency; the queue and the business data share one durable store and one backup. The outbox is kept (rather than polling jobs directly) so the tested Phase 06 flow and its failure handling stay identical. Queue throughput is bounded by one worker, which is the design limit anyway | More than one worker machine, or queue depth that makes single-row relay too slow |
| ADR-017 | Native worker (`app/worker_native.py`): each job is `python -m worker.transcode` in a child process inside a Windows Job Object (kill-on-close, memory cap, CPU affinity = `FFMPEG_THREADS` CPUs, below-normal priority); heartbeat every 3 s extends the lease and stores measured progress. One worker instance (PostgreSQL advisory lock), one job at a time | Docker/WSL2 are excluded on the VPS. The Job Object gives the two things the container gave for reliability: a hard resource bound and guaranteed cleanup of FFmpeg when the worker dies. Measured: `-threads 2` alone still used 3.2 cores; with affinity 1.8. Lost versus the container: no filesystem or network isolation for the decoder | A decoder vulnerability becomes a concern; need for more than one concurrent job |
| ADR-018 | Local accounts in PostgreSQL (`AUTH_PROVIDER=local`): scrypt password hashes, opaque bearer session tokens stored as SHA-256, 5-failure lockout, per-IP attempt limit, CLI-only account creation. Firebase verification stays available as `AUTH_PROVIDER=firebase` and remains the code default so Phase 03 tests are unchanged | No Firebase project ever existed and the Admin SDK needs Google credentials, which conflicts with ADR-015. Bearer tokens in page memory avoid cookies and therefore CSRF. Costs: we now own password storage and reset; no self-service sign-up or password reset flow; IP limiter is per-process memory | Need for self-service accounts, MFA or SSO |
| ADR-019 | Upload limit is configuration (`MAX_UPLOAD_BYTES`): code default stays 50 MB (brief's dataset limit, Phase 01–06 tests), the VPS template sets 200 MB (owner request). The 30-second duration limit is unchanged. Hashing is streamed and verified hashes are cached per (size, mtime) | Keeps earlier behaviour and tests while allowing larger sources on the VPS without loading files into memory or re-hashing on every Range request. A 200 MB source still must be at most 30 s | Instructor requires a hard 50 MB limit in the deployed demo: set `MAX_UPLOAD_BYTES=50000000` |
| ADR-021 | **Deployment target is AWS, fully cloud-hosted** (owner decision, 2026-11-20, after re-reading the brief). Supersedes ADR-015 for production; ADR-016/017/018 remain as the local/VPS mode. Planned mapping: ALB -> ECS Fargate `api`; RDS for PostgreSQL in private subnets; private versioned S3 with presigned POST/GET; SQS + dead-letter queue fed by the existing outbox relay; one long-running Fargate `worker` service (FFmpeg in the container, one job at a time); Cognito verified through a generic OIDC/JWKS verifier; Secrets Manager; Terraform in `infra/aws/`; GitHub Actions. Fargate tasks in public subnets without a NAT Gateway. Details and open points: `docs/AWS_ARCHITECTURE.md`. **Nothing is built or applied yet** | The brief requires one of AWS/Azure/GCP, a cloud-hosted site, container-based transcoding and infrastructure from code; the VPS met none of the four. Reusing the storage/broker/verifier interfaces keeps the tested reliability code unchanged. Costs: monthly AWS charges where the VPS was already paid; more moving parts; the always-on worker task is not literally "one task per conversion"; public-subnet tasks trade network isolation for no NAT cost; VPS data is not migrated | Account turns out to be a Learner Lab (no custom IAM roles, possibly no Cognito/GitHub OIDC); instructor requires per-job tasks; measured cost exceeds the owner's budget |
| ADR-022 | Phase 07 AWS adapter choices. (a) Backends are selected by `STORAGE_BACKEND` (`local`/`s3`), `QUEUE_BACKEND` (`postgres`/`sqs`), `AUTH_PROVIDER` (`firebase`/`local`/`cognito`); local stays the default. (b) Upload is an S3 **presigned POST** with `content-length-range` and a fixed Content-Type; playback is a presigned GET pinned to the output's **VersionId**; `source_generation` is the input object's VersionId, so the bucket must be versioned and deleting a video deletes every version. (c) Identity is the Cognito **ID token's verified e-mail** (lower-cased), `admin` comes from the `admin` group; the browser sends the password straight to Cognito (`USER_PASSWORD_AUTH`). (d) `SqsBroker` uses 2-second long polling, a 300 s visibility timeout extended from the worker heartbeat, and an explicit dead-letter send for malformed messages; delivery exhaustion is left to the queue's redrive policy. (e) New dependencies: `boto3`, and `PyJWT[crypto]` made explicit (it was already installed through `firebase-admin`) | (b) lets S3 enforce size and type before any byte reaches the API, and pinning versions keeps "outputs identified by source version and profile" true on S3. (c) keeps sharing-by-e-mail and existing `owner_uid` values working; e-mail is only safe as an identity because accounts are created by an administrator and unverified e-mails are refused. (d) keeps the worker loop unchanged and the idle request rate low. Costs: three duck-typed branches (`hasattr(store, "download")`, `hasattr(store, "root")`, `getattr(broker, "extend")`); the account-management page does not manage Cognito users; `/api/monitor` cannot report SQS dead letters | Self-service sign-up or e-mail changes are enabled in Cognito (switch identity to `sub`); more than one worker; need for dead-letter counts in the app |
| ADR-023 | Phase 08 Terraform (`infra/aws/`, validated, **not planned or applied**). (a) Region `ap-southeast-2` (Sydney): the owner first chose `ap-southeast-1`, but the AWS account is a "project" set up in Sydney and its sign-in page refuses Singapore ("not supported for your project"), so the owner agreed to Sydney on 2026-11-20; higher latency from Vietnam is accepted. (b) HTTPS: ACM certificate for the owner's domain on the ALB, DNS validation record added by hand at the registrar (DNS is outside AWS); port 80 only redirects; HSTS and the hidden `Server` header are set by the ALB listener. No CloudFront. (c) DB password: `random_password` stored in Secrets Manager and in local, gitignored Terraform state; the application connects as the RDS master user `video_portal`. (d) Both ECS services start at `desired_count = 0` and ECR tags are immutable; images are pushed first, then the count is raised. (e) Worker deploys stop-then-start (0–100 %) because of the single-worker lock; API deploys use the ECS circuit breaker with rollback. (f) S3: versioning, Block Public Access, TLS-only bucket policy, CORS limited to the site origin, non-current versions expire after 7 days. (g) PostgreSQL major version `18` on `db.t4g.micro` (the project's tests ran on 18.7; `describe-orderable-db-instance-options` confirmed the class for 18.6 in Sydney). Still unverified until `apply`: Free-plan eligibility of each service | (b) the owner already has a domain, so the ALB gets a publicly trusted certificate without an extra service. (c) is the simplest approach a student team can read and operate; rotation-managed secrets would restart-break long-running tasks. (d) avoids crash-looping tasks and their cost before images exist. Costs: the password is readable in the state file; the app has more database privilege than it needs; `apply` blocks until the DNS record exists; a second run is needed to start the services | First real `plan`/`apply` rejects an assumption; instructor asks for a least-privilege DB role or remote state; Phase 12 CI needs to register task definitions outside Terraform |
| ADR-020 | `APP_ENV=production` now means "VPS with private local storage" and is allowed when `STORAGE_ROOT`/`WORK_ROOT` are absolute and outside the application directory; `K_SERVICE` (Cloud Run) is still refused. `init-db` is the migration mechanism: create missing tables, `ADD COLUMN IF NOT EXISTS`, and ensure the single default profile | The Phase 04/06 guard that refused every non-local environment existed because local disk is not durable on Cloud Run; on a VPS the local disk is the durable store. Additive-only schema changes keep rollback of code safe without a migration tool | A destructive or data-rewriting schema change is ever needed (then adopt a real migration tool) |
| ADR-024 | **Deployment target is Azure; AWS is dropped** (owner decision, 2026-11-21: drop AWS and do Azure only). Supersedes ADR-021/022/023 for production; ADR-016/017/018 remain as the local/VPS mode. Planned mapping: Container Apps app `api` with external HTTPS ingress, scaled to zero when idle; Azure Database for PostgreSQL flexible server with private access in a VNet shared with the Container Apps environment; private versioned Blob Storage with user delegation SAS (browser `PUT`, read SAS pinned to the blob version); Service Bus queue with its built-in dead-letter queue; conversion as an **event-driven Container Apps Job** (one job per execution, replica timeout, platform retry limit 0) plus a scheduled `maintenance` job, with the API relaying the outbox right after commit; Microsoft Entra External ID through the existing generic OIDC/JWKS verifier with authorization code + PKCE in the page; Key Vault; two user-assigned managed identities; Terraform in `infra/azure/`; GitHub Actions. The AWS material stays in the repository as archived reference and on the frozen `aws` branch; the AWS adapter modules are removed in Phase 07 when their Azure replacements pass tests. Details, checked sources and open points: `docs/AZURE_ARCHITECTURE.md`. **Design only: no Azure account checked, no Azure code, nothing built or applied** | The brief allows any of the three providers and names these Azure services. Per-conversion jobs follow the brief's "bounded Container Apps Jobs" wording, which the always-on AWS worker did not, and leave nothing running between videos. Reusing the storage/broker/verifier interfaces keeps the tested reliability code unchanged. Costs: the finished AWS adapters, 13 Terraform files and their tests are thrown away; the worker needs a run-once mode and a scheduled job; a SAS cannot cap upload size, so the limit is enforced only at `complete`; sign-in leaves the page; the API is on Container Apps where the brief suggests App Service; every job start pays container start-up and KEDA polling delay (not measured); VPS data is not migrated | The subscription cannot create an external tenant (then local accounts, as a written deviation needing instructor approval); Service Bus Basic or managed-identity scale rules prove insufficient for jobs; the instructor requires App Service for the API; measured cost exceeds the owner's credit |
| ADR-025 | Phase 07 Azure adapter choices (code only, no Azure call made). (a) Backends are selected by `STORAGE_BACKEND` (`local`/`blob`), `QUEUE_BACKEND` (`postgres`/`servicebus`), `AUTH_PROVIDER` (`firebase`/`local`/`oidc`); local stays the default and runs without the Azure packages installed. The AWS adapters, their tests, `boto3`, `deploy/aws/` and the AWS CI job are removed from `main`. (b) Upload is a browser `PUT` to a **user delegation SAS** with create permission on one blob; every backend now returns `upload_headers` and the page sends them, so local and Blob Storage share one code path. Playback is a read SAS on the blob **version** (`sr=bv` + `versionid`). `source_generation` is the blob version ID; deleting a video deletes the current blob, then every version. Size and type are enforced at `complete`, which deletes an oversized blob. (c) `ServiceBusBroker`: peek-lock, `message_id` = outbox event ID, lock renewed from the worker heartbeat at most every 20 s, explicit dead-lettering of malformed messages; delivery exhaustion is left to the queue's `MaxDeliveryCount`. No message counts in the API (they need namespace management rights). (d) The worker gets `--once` (reconcile, relay one event, one message, exit; failures exit non-zero) and a `maintain` command; with Service Bus the API relays the outbox right after `complete` commits; `DISPATCH_SECONDS` is configurable (300 in the Azure image). (e) OIDC is generic: issuer, client ID, JWKS, authorize, token and optional logout URLs are explicit `https` settings taken from the tenant's discovery document, not derived from a tenant name. The page does authorization code + PKCE with `state` and `nonce` without any library; identity is the lower-cased e-mail claim, admin is an app role | One interface per concern keeps the tested pipeline untouched. Explicit OIDC URLs avoid baking an unverified Entra URL format into code and let the same code be tested against a local fake provider. A hand-written PKCE flow (about 60 lines) avoids shipping MSAL under a `default-src 'self'` policy. Costs: three SDK packages instead of one; the Service Bus adapter is tested only against an in-memory fake (AMQP cannot be stubbed like HTTP); the API cannot verify that an e-mail was verified by the tenant; scripts cannot sign in through a redirect and need an ID token in `PORTAL_ID_TOKEN`; the token lives in page memory, so a reload means signing in again | First run against real Azure shows a wrong assumption (SAS create-only semantics, version deletion, lock renewal, claim names); the tenant cannot guarantee verified e-mails; instructor requires message counts in the portal |
